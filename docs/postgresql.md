# PostgreSQL 18

Compose использует `postgres:18.6-alpine` (стабильный релиз на 09.09.2026).
Ветка 18 поддерживается до 14.11.2030; минорные обновления внутри неё всё равно
нужно устанавливать. [Политика версий](https://www.postgresql.org/support/versioning/).

В официальном образе 18 изменились пути:

| Установка | Compose volume | Mount | PGDATA |
| --- | --- | --- | --- |
| прежняя production 14 | `db` | `/var/lib/postgresql/data` | `/var/lib/postgresql/data` |
| новая production/dev 18 | `db18` | `/var/lib/postgresql` | `/var/lib/postgresql/18/docker` |

Не подставляйте образ 18 к старому каталогу данных. Новый `db18` сам по себе
не переносит истории из `db`. Не запускайте инициализацию схемы на пустом `db18`
вместо восстановления production. [Документация образа](https://hub.docker.com/_/postgres).

## Перенос существующей установки

Используется обычный `pg_dump` / `pg_restore`: для этой небольшой базы это проще
репликации, не требует промежуточных версий 15–17 и заново строит индексы.
На новом кластере остаются включёнными checksums — значение по умолчанию в 18.

1. Проверьте фактические контейнеры, тома, размер БД, свободный диск, роли,
   расширения и все приложения, которые пишут в БД. Сохраните Compose/env
   текущей установки и резервную копию **на другом диске/хосте**. Секреты и
   дампы должны быть доступны только владельцу и никогда не попадать в Git.
2. Загрузите образ 18 заранее. Поднимите отдельный контейнер без опубликованных
   портов, с новым томом `db18` и теми же DB/user/password. Старый том не трогайте.
3. Пока сайт работает, сделайте custom dump (`pg_dump -Fc`) и восстановите его
   в отдельный контейнер через `pg_restore --exit-on-error --jobs=4`.
   Проверьте приложение, расширения и схему с `TYPEORM_SYNCHRONIZE=false`.
   Пишущие integration-тесты выполняйте только на отдельной **синтетической**
   базе `_test`, не на копии с реальными пользовательскими данными.
4. Перед финальным дампом исключите **всех** писателей. На `dobro` для этого
   рабочий контейнер 14 останавливается и его том временно открывается тем же
   образом 14 в контейнере `--network none` без TCP-listener. Никогда не
   запускайте два PostgreSQL одновременно на одном каталоге данных.
5. Сделайте свежий финальный дамп через локальный Unix socket этого контейнера.
   Сохраните вывод `check-database.sql`. Восстановите дамп в **изолированную
   новую БД**, удалив только её репетиционную копию:

   ```bash
   pg_restore --exit-on-error --clean --if-exists --create --jobs=4 \
     -U DB_USER -d postgres /backup/final.dump
   ```

6. Повторите `psql -X -qAt -v ON_ERROR_STOP=1 -f check-database.sql` на новой БД
   и сравните результаты: число и контрольные суммы всех строк, sequences,
   индексы, ограничения и расширения. `NOT NULL` исключены из сравнения
   `pg_constraint`: только в 18 они стали отдельными объектами этого каталога.
   Проверьте также роли, настройки БД, locale и отсутствие изменений схемы ORM.
7. Остановите оба временных DB-контейнера. Проверьте `POSTGRES_VERSION=18.6`
   в `.env`, новый mount и правильное имя заполненного тома в Compose.
   Запустите **только** `db`: `docker compose up -d --no-deps --no-build --wait db`.
   Проверьте `/api/story?limit=1`, `/health`, главную страницу и браузерные тесты.
   Если приложение не переподключилось, перезапустите только `app`.
8. Выполните `vacuumdb --analyze-only`, сохраните финальный дамп вне сервера
   и убедитесь, что проверки и мониторинг успешны. Удаляйте только созданные
   для миграции временные контейнеры/файлы, не старый рабочий том.

На `dobro` репетиция 14.24 → 18.6 заняла 12 с для дампа и 43 с для restore.
Production перенесён 09.09.2026: финальное восстановление заняло 40 с,
вся недоступность API каталога — около 4 минут. Главная страница и отдельный
inference API продолжали работать. Приложение переподключилось без рестарта;
все проверки данных совпали, ORM не предлагает изменений схемы.
Дамп без сжатия занимает около 1.3 GB: при ограниченном диске он создавался
на отдельном защищённом tmpfs, после чего копировался на другой хост.
tmpfs не является постоянной резервной копией. Результаты зависят от диска/CPU.

## Откат

До допуска записей в 18 можно остановить новый контейнер и запустить 14.24 со
старым томом и сохранённым Compose. `db` и `db18` независимы; `--link` не используется.
Не возвращайте приложение к 14 после новых записей в 18: старый том отражает
только момент переключения. Такой откат потеряет новые данные и требует
отдельного плана переноса/восстановления. Старый том не удаляется автоматически.

В `docker-compose-dev.yml` теперь также используется 18. Для существующей dev-БД
17 нужен такой же dump/restore либо **явно согласованный** запуск пустой БД.
Обновление production не мигрирует отдельный сайт `dev.porfirevich.ru`.
